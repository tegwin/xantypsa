# VibePSA — Deployment

Deploying to Vercel. The same codebase runs locally with no changes — Supabase
provides the database and authentication in both cases, so there is no
environment-specific code path.

Setting up from scratch? Start with [INSTALL.md](./INSTALL.md).

---

## Before you deploy

Confirm the production build passes locally. Vercel runs exactly this, and it
catches a class of error `tsc` does not — invalid route exports, missing Suspense
boundaries, and server-only modules leaking into client bundles:

```bash
npm run build
```

## Environment variables

Set these in **Vercel → Project → Settings → Environment Variables** for
Production, Preview, and Development. Keep the same values in your local `.env`.

| Variable | Source | Notes |
|---|---|---|
| `DATABASE_URL` | Supabase → Settings → Database → **Transaction** pooler (6543) | Must end `?pgbouncer=true`. Serverless needs the pooler — a direct connection will exhaust under load. |
| `DIRECT_DATABASE_URL` | Same page → **Session** pooler (5432) | Used only by `prisma db push` / `migrate`. |
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Settings → API → Project URL | Public. |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase → Settings → API → `anon` | Public by design — row-level security is what protects data, not this key's secrecy. |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Settings → API → `service_role` | **Secret.** Bypasses all row-level security. Never expose to the browser or prefix with `NEXT_PUBLIC_`. |
| `AI_ENCRYPTION_KEY` | `openssl rand -hex 32` | Encrypts stored LLM provider keys. **Use the same value in every environment** — a different key makes existing provider keys undecryptable. |

**No longer used:** `NEXTAUTH_URL` and `NEXTAUTH_SECRET`. Authentication moved to
Supabase Auth and the `next-auth` dependency has been removed. Delete them from
Vercel if they're still set.

## Supabase configuration

### Redirect URLs

Password reset and confirmation links are generated by Supabase and must point
back at the right origin. **Authentication → URL Configuration**:

- **Site URL** — your production URL, e.g. `https://vibepsa.vercel.app`
- **Redirect URLs** — add each origin the app runs on:
  - `http://localhost:3000/auth/callback`
  - `https://<production-domain>/auth/callback`
  - `https://*-<vercel-team>.vercel.app/auth/callback` — preview deployments

Miss the localhost entry and reset works in production but not on your machine.
Miss the preview wildcard and it breaks on every PR deployment.

### Email — sending from your own domain

Out of the box, auth emails come from **`noreply@mail.app.supabase.io`** with the
sender name **"Supabase Auth"** and an *"Opt out of these emails"* footer. That
shared sender is also **rate-limited and intended for development only** — it is
not something to put in front of customers.

Two changes remove the Supabase branding entirely.

**1. Custom SMTP** — *Authentication → Emails → SMTP Settings → Enable Custom SMTP*

Fill in your provider's host, port, username and password, then set:

- **Sender email** — e.g. `noreply@yourdomain.com`
- **Sender name** — e.g. `VibePSA`

This replaces the from-address, the sender name, and drops the opt-out footer
(that line is added by Supabase's shared sender, not by the template). It also
lifts the rate limit.

Any transactional provider works — Resend, Postmark, SendGrid, Mailgun, AWS SES,
or Microsoft 365 if you're already there.

**2. Email templates** — *Authentication → Emails → Templates*

Rewrite the default "Follow this link to reset the password for your user" copy
with your own wording and HTML. There is a template per flow (reset, confirm,
invite, magic link, email change). Keep the `{{ .ConfirmationURL }}` placeholder
— that is the actual link.

**Then authenticate the domain.** In your email provider, add the SPF and DKIM
records for `yourdomain.com`. Without them, mail sent as your domain from their
servers lands in spam. This is the step most often skipped, and it is the reason
"the emails work but nobody receives them".

Send yourself a password reset afterwards to confirm the from-address, the
branding, and deliverability all in one go.

## Deploying

Vercel auto-detects Next.js; no `vercel.json` is required. `prisma generate`
runs from the `postinstall` script, so the client is always built against the
current schema.

**Schema changes are not applied automatically.** Run them against the target
database yourself:

```bash
npx prisma db push          # development
npx prisma migrate deploy   # production, once you adopt migrations
```

Adopting migrations before real customer data is worth the small effort — `db
push` has no history and no rollback.

## After the first deploy

1. Sign in and confirm the session survives a refresh.
2. Reset your own password end to end — this is the quickest way to prove the
   redirect URLs and SMTP are right.
3. Re-add your AI provider under **Settings → AI**. Provider keys are encrypted
   with `AI_ENCRYPTION_KEY` and stored per environment; if production has a
   different key, the keys entered locally will not decrypt there.

## Known constraints

**Self-hosted AI models cannot run on Vercel.** Serverless functions can't host
inference. The `local` provider must point at a machine you control, or use
Anthropic/OpenAI in production. This is a platform limit, not a configuration
problem.

**The AI SQL tool is guarded by application validation, not by the database.**
`run_analytics_query` enforces SELECT-only, single-statement, and a mandatory
`"tenantId" = $1` parameter, and blocks inlined tenant ids. That is validation,
not a security boundary. **Before real customer data, add PostgreSQL row-level
security and a dedicated read-only role** so tenant isolation is enforced by
Postgres rather than by a regex.

**The AI chat route runs a multi-step tool loop** and sets `maxDuration = 300`.
Vercel's Hobby plan caps functions at 60 seconds — long analytical questions
will time out there. Pro or above is needed for the full window.

## Operational gotchas

- **Restart after adding a Prisma model or editing `.env`.** Next reads `.env`
  at startup and Node caches the Prisma client at boot, so a running process
  keeps the stale copy and throws `Cannot read properties of undefined
  (reading 'findFirst')`. Applies locally; on Vercel each deploy is a fresh boot.
- **Supabase free-tier projects pause after inactivity.** A paused project looks
  exactly like a bad connection string. Check the dashboard before debugging the
  URL.
- **Route files may only export request handlers.** Exporting a helper from a
  `route.ts` fails the production build but passes `tsc` — so it will not show up
  until deploy time. Put shared code in `lib/`.

## Stack reference

- **Next.js 14** — App Router, server components, API route handlers
- **TypeScript 5** — strict off, `noImplicitAny` off
- **React 18**
- **Prisma 5** — ORM, `prisma/schema.prisma` is the source of truth
- **PostgreSQL** — hosted on Supabase
- **Supabase Auth** — `@supabase/ssr`, cookie sessions refreshed in middleware
- **Tailwind CSS 3** — dark-mode-first, custom `brand` + `surface` palettes
- **Geist Sans / Geist Mono** — fonts, loaded as CSS variables
- **lucide-react** — icons
- **@tanstack/react-table** — data tables
- **Recharts** — charts
- **jsPDF + jspdf-autotable** — quote and invoice PDFs
- **react-hot-toast** — notifications
- **Zod** — validation
- **date-fns** — date handling
- **clsx + tailwind-merge** — class composition via `cn()`
- **@anthropic-ai/sdk** — Anthropic provider (primary)
- **openai** — OpenAI provider (primary) and any OpenAI-compatible server
- **@modelcontextprotocol/sdk** — MCP server (in progress)
- **nodemailer** — outbound app email (separate from Supabase auth email)

The full breakdown, including the Tailwind palette, the shared component classes
in `globals.css`, and the project layout, is in
[INSTALL.md → The stack](./INSTALL.md#the-stack).
